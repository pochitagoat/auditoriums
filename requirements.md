## 1. Назначение и границы проекта

Приложение предназначено для сотрудников отдела, отвечающего за компьютеры и техническое оснащение университета. Пользователей немного, все относятся к одному отделу.

Основной сценарий:

1. Сотрудник во время обхода открывает приложение в браузере телефона или ноутбука.
2. Находит аудиторию по названию или фильтрам и открывает ее карточку.
3. Сверяет сведения об аудитории и оборудовании с фактическим состоянием.
4. Создает или исправляет записи, добавляет фотографии, при необходимости списывает оборудование.
5. При каждой операции изменения данных вручную указывает свое ФИО.

Приоритеты: понятный код, простая архитектура, сохранность существующих данных и удобство работы с телефона.

В первую версию не входят:

- авторизация, учетные записи, роли и права доступа; Spring Security, JWT и OAuth;
- React, Vue, Angular, TypeScript, SPA и отдельная frontend-сборка;
- Lombok и Java `record`;
- микросервисы, Kubernetes, Redis, Kafka и сложные enterprise-паттерны;
- интеграция с расписанием, полный журнал изменений, самостоятельный учет каждого периферийного устройства рабочего места;
- production-развертывание, настройка домена и инфраструктуры сервера.

Приложение впоследствии будет размещено на сервере. С компьютера и телефона пользователи будут открывать один адрес приложения. Сейчас требуется подготовить приложение к такому запуску, но само размещение на сервере является отдельной задачей.

## 2. Стек и существующий проект

Использовать Java 21, Spring Boot, Spring MVC, Thymeleaf, Spring Data JPA, Hibernate, PostgreSQL, Flyway, Bean Validation, Maven, HTML, CSS, обычный JavaScript, Docker и Docker Compose.

Проект уже существует. На момент подготовки требований:

- в `pom.xml` указан Spring Boot `4.1.1` и Java 21;
- основной Java-пакет — `rut.iuct.auditoriums`;
- JPA-модели находятся в `src/main/java/rut/iuct/auditoriums/model/`;
- исходная схема оформлена в `src/main/resources/db/migration/V1__create_auditorium_schema.sql`;
- настройки находятся в `src/main/resources/application.properties`;
- существуют Maven Wrapper и скрипт демонстрационных данных.

Развивать текущий проект. Сохранить существующие версии и формат конфигурации, если нет конкретной причины менять их. Добавить необходимые зависимости Thymeleaf и Validation. Изменение версии, зависимости или структуры должно иметь понятное обоснование; обновление ради обновления не требуется.

Демонстрационные данные использовать только в специально подготовленной тестовой БД, без автоматической загрузки в существующую рабочую БД.

## 3. Архитектура и взаимодействие frontend с backend

### 3.1. Два назначения контроллеров

MVC-контроллеры с `@Controller` обрабатывают открытие страниц и возвращают HTML, сформированный Thymeleaf. Данные для отображения получают непосредственно из сервисов.

REST-контроллеры с `@RestController` под `/api/**` предоставляют JSON API. Все операции изменения данных, включая создание, редактирование, списание, восстановление, удаление и загрузку фотографий, выполняются через REST API.

Оба вида контроллеров используют общие сервисы. MVC-контроллеры не делают HTTP-запросы к REST API собственного приложения. Контроллеры не содержат бизнес-логику и не обращаются к репозиториям напрямую.

Открытие страницы:

```text
Браузер -> MVC-контроллер -> сервис -> репозиторий -> PostgreSQL
                     -> Thymeleaf -> HTML в браузере
```

Сохранение формы:

```text
HTML-форма -> небольшой JavaScript -> REST API -> сервис -> репозиторий -> PostgreSQL
```

Для каждой операции изменения есть один серверный обработчик в REST API. Дублирующие MVC-обработчики сохранения форм не создавать. GET-запросы не изменяют данные.

### 3.2. JavaScript

JavaScript разрешен там, где упрощает работу. Использовать небольшие понятные скрипты для отправки форм через `fetch`, подтверждений, загрузки файлов и отображения ответов API. Получать отдельное разрешение на каждое такое применение JavaScript не требуется.

Страницы, поиск, фильтры, навигация и пагинация остаются серверными. После успешного изменения достаточно перейти на нужную страницу или перезагрузить карточку. Полную клиентскую модель данных и SPA не создавать.

Отправка изменений в выбранной архитектуре требует JavaScript. При его отключении интерфейс должен понятно сообщать, что сохранение недоступно; отдельный путь сохранения через MVC не требуется.

Общий код отправки запросов и показа ошибок можно вынести в небольшой общий модуль, а особенности страниц — в отдельные скрипты. На время запроса блокировать повторное нажатие кнопки отправки. При ошибке сохранять введенные значения и показывать ошибки рядом с соответствующими полями, а общую ошибку — возле формы.

### 3.3. Организация Java-кода

Слои: Controller -> Service -> Repository -> Database. Entity, DTO и Mapper имеют отдельные назначения.

В основном пакете использовать существующий `model/` для JPA-сущностей и добавлять по мере необходимости:

```text
controller/mvc/
controller/api/
service/
repository/
dto/
mapper/
exception/
validation/
config/
storage/
```

Не переименовывать существующие пакеты только ради этой схемы. Бизнес-сервисы могут быть обычными классами. Интерфейс и единственную реализацию `ServiceImpl` для каждого сервиса создавать не требуется. Интерфейс нужен для сменяемого файлового хранилища.

Entity и REST DTO разделять. JPA-сущности через REST напрямую не возвращать. DTO писать обычными Java-классами с конструкторами, getter и setter. Использовать понятные ручные mapper-классы; отдельный генератор маппинга не требуется.

Сервисный слой выполняет проверки бизнес-правил, обновляет аудит и управляет транзакциями. Не дублировать эти правила между MVC, REST и JavaScript.

## 4. Исходная схема и работа с существующими данными

Исходный SQL находится в `src/main/resources/db/migration/V1__create_auditorium_schema.sql`. Эта миграция является исторической основой, а не конечной схемой после реализации новых требований.

Исходные таблицы: `auditorium`, `auditorium_photo`, `projector`, `workstation`, `printer`, `department`, `additional_equipment`, `auditorium_department`, `auditorium_additional_equipment`. Идентификаторы — `BIGINT` с identity. Имеющиеся внешние ключи, ограничения и индексы учитывать при миграции.

Связь с кафедрой перенести из `auditorium_department` в `auditorium.department_id`. Справочник `additional_equipment` и таблицу связи `auditorium_additional_equipment` сохранить. В JPA связь дополнительного оборудования оформить отдельной Entity связи, без `@ManyToMany`, как описано в разделе 5.

Правила изменений схемы:

1. Не считать существующую БД пустой и не пересоздавать ее.
2. Не изменять уже примененную `V1` и другие примененные миграции.
3. Все изменения оформлять новыми Flyway-миграциями в существующей папке.
4. До применения описать изменение, показать SQL и объяснить влияние на старые данные.
5. Проверить миграции на чистой БД и на отдельной копии БД с прежней схемой и данными.
6. Перед применением к реальным данным подготовить согласованную резервную копию БД и фотографий.
7. Не включать Hibernate `create`, `create-drop` или автоматическое изменение схемы вместо Flyway; использовать проверку соответствия модели схеме.

Если существующая БД создана вне Flyway, сначала проверить ее соответствие исходной миграции. Baseline устанавливать контролируемо для проверенной базы. Автоматически считать любую непустую БД соответствующей `V1` нельзя.

Проверка копии данных должна выявлять неоднозначные связи кафедр, повторяющиеся инвентарные номера, нарушения целостности связей дополнительного оборудования и расхождения старых признаков с детальными записями. Составлять отчет с идентификаторами записей. Не разрешать конфликты произвольным выбором и не удалять данные для успешного прохождения миграции.

## 5. Целевая модель данных

### 5.1. Аудитория

Сохранить существующие поля `auditorium`:

| Поле | Значение и правила |
| --- | --- |
| `id` | Идентификатор, формируется БД |
| `name` | Название аудитории, обязательное, до 255 символов; например, `305а` |
| `type` | Обязательный тип из существующего PostgreSQL enum |
| `description` | Необязательное текстовое описание |
| `capacity_students` | Обычные места для студентов, целое число не меньше нуля |
| `capacity_students_extra` | Дополнительные места при добавлении стульев, целое число не меньше нуля |
| `capacity_staff` | Места для преподавателей и сотрудников, целое число не меньше нуля |
| `building` | Корпус, до 255 символов |
| `floor` | Этаж, целое число; отрицательный этаж допустим |
| `area` | Площадь в квадратных метрах, конечное число не меньше нуля |
| `screen_size` | Размер экрана, текст до 255 символов |
| `has_ac` | Признак наличия кондиционера |
| `internet` | Признак наличия интернета |
| `subnet` | Сетевая подсеть, текст до 255 символов |
| `in_schedule` | Используется ли аудитория для занятий по расписанию |
| `equipment_issue` | Свободное описание проблемы с оборудованием, до 2048 символов |
| `schedule_link` | Ссылка на расписание, до 2048 символов; сохранить для будущего использования |
| `actual_schedule_link` | Дополнительная ссылка на расписание, до 2048 символов; сохранить |
| `has_projector` | Старый признак, сохранить для совместимости; не использовать для новых расчетов |
| `pc_count_manual` | Старое число компьютеров, сохранить для совместимости; если задано, не меньше нуля |
| `last_modified` | Время последнего изменения, назначается сервером |
| `changed_by` | ФИО сотрудника, выполнившего последнее изменение, до 255 символов |

Добавить `department_id`, `board_type` и `version`.

При создании обязательны только `name`, `type` и ФИО автора операции. Остальные пользовательские поля могут быть не заполнены. Название хранить строкой и не ограничивать форматом номера. Глобальную уникальность названия аудитории не вводить: одинаковые названия могут встречаться в разных корпусах.

Неизвестное необязательное значение хранить как `NULL`. Для чисел ноль является известным значением, отличным от неизвестного. Для `has_ac`, `internet`, `in_schedule` использовать три состояния: «Да», «Нет», «Не указано».

В таблице аудиторий показывать обычные студенческие места. В карточке отдельно показывать обычные, дополнительные и места для сотрудников. Сумма обычных и дополнительных студенческих мест доступна как вычисляемое значение; если хотя бы один компонент неизвестен, не представлять неполную сумму как известную полную вместимость.

`has_ac` является самостоятельным признаком помещения. Свободное название записи дополнительного оборудования не использовать для автоматического определения этого признака; отдельный дублирующий справочник кондиционеров не создавать.

`schedule_link` и `actual_schedule_link` пока не показывать и не редактировать в интерфейсе. Их существующие значения не терять при сохранении остальных полей аудитории.

### 5.2. Тип аудитории

Сохранить существующий PostgreSQL enum `auditorium_type`. Значения фиксированы; через интерфейс новые типы не добавлять.

| Значение | Подпись в интерфейсе |
| --- | --- |
| `CLASSROOM` | Обычная аудитория |
| `COMPUTER_CLASSROOM` | Компьютерная аудитория |
| `MULTIMEDIA_LECTURE_HALL` | Мультимедийная лекционная аудитория |
| `PRACTICAL_CLASSROOM` | Аудитория для практических занятий |
| `SERVICE_ROOM` | Служебное помещение |
| `SPECIAL_LABORATORY` | Специализированная лаборатория |
| `SPECIAL_PURPOSE_ROOM` | Помещение специального назначения |

### 5.3. Кафедра

`department`: `id`, обязательное непустое `name` до 255 символов, необязательное `mol_link` до 2048 символов. Добавить поля последнего изменения и `version`.

Одна аудитория связана максимум с одной кафедрой, одна кафедра — со многими аудиториями. Реализовать `Auditorium -> Department` через `@ManyToOne` и nullable `auditorium.department_id`. Отсутствующая кафедра допускается, в том числе для старых данных.

Миграция прежней `auditorium_department`:

- нет связи — оставить `department_id = NULL`;
- одна связь — перенести ее;
- несколько связей — сформировать список конфликтов и потребовать явного решения для каждой аудитории перед завершением перехода;
- сохранить исходные связи до проверки корректности переноса; неоднозначные связи не отбрасывать.

CRUD кафедр вынести в отдельный раздел. В форме аудитории выбирать кафедру из выпадающего списка; создание кафедры внутри этой формы не требуется. Удаление используемой кафедры запрещено, пока аудитории ссылаются на нее.

### 5.4. Рабочее место

`workstation` — компьютерное рабочее место целиком. Поля: `id`, обязательный `auditorium_id`, необязательные `pc_name`, `monitors`, `keyboards`, `mice`, `location_info`; текстовые поля — до 255 символов.

- `pc_name` означает инвентарный номер компьютера, а не сетевое имя.
- `monitors`, `keyboards`, `mice` остаются текстовыми описаниями устройств или моделей.
- `location_info` помогает найти место, например «третий ряд, место слева».
- Списание применяется ко всему рабочему месту. Отдельных сущностей для мониторов, клавиатур и мышей в этой версии не создавать.
- Пустой инвентарный номер допустим. Для непустых номеров обеспечить уникальность после проверки старых данных; выявленные старые дубликаты сначала разобрать, не исправляя их автоматически.
- В общий поиск аудиторий инвентарный номер не включать.

Добавить общие поля оборудования из раздела 5.7. Одна аудитория может иметь несколько рабочих мест.

### 5.5. Проектор и принтер

`projector`: `id`, обязательный `auditorium_id`, необязательные `model`, `mol`, `warehouse` до 255 символов. `mol` — материально ответственное лицо, `warehouse` — склад или учетное место оборудования.

`printer`: `id`, обязательный `auditorium_id`, необязательные `model`, `warehouse` до 255 символов и `cartridge_link` до 2048 символов.

Для обеих таблиц добавить общие поля оборудования из раздела 5.7. В аудитории может быть несколько проекторов и несколько принтеров.

### 5.6. Дополнительное оборудование

Сохранить исходную модель: `additional_equipment` — справочник типов оборудования, например «Колонки» или «Сканер». Поля предметной модели: `id` и обязательное непустое `name` до 255 символов. Сведения о последнем изменении справочника и `version` предусмотрены общими требованиями к аудиту и одновременному редактированию.

`auditorium_additional_equipment` хранит связь аудитории с типом: `auditorium_id`, `additional_equipment_id`, составной первичный ключ и существующие внешние ключи. Один тип может быть выбран для нескольких аудиторий, а аудитория может иметь несколько типов. В JPA использовать отдельную Entity связи с двумя `@ManyToOne`; `@ManyToMany` не использовать.

Списание и восстановление дополнительного оборудования пока не реализуются. Не добавлять `status`, `written_off_at`, `written_off_by` ни в справочник, ни в таблицу связи. Общие поля списываемого оборудования из раздела 5.7 к ним не относятся.

Не преобразовывать справочник в конкретные экземпляры оборудования, не добавлять к нему `auditorium_id`, не клонировать записи по аудиториям и не переименовывать таблицы для такого перехода. Сохранить существующие идентификаторы, справочные записи, в том числе неиспользуемые, и связи.

В интерфейсе аудитории можно выбрать несколько типов и снять выбор ранее указанного типа. Снятие выбора удаляет только связь, а не запись справочника, и не является списанием. Количество отдельных предметов не учитывается. Удаление используемого типа из справочника запрещено, пока на него ссылаются аудитории.

### 5.7. Общие поля и правила оборудования

Правила списания и поля этого раздела применяются к `workstation`, `projector`, `printer`. Дополнительное оборудование сохраняет модель справочника без списания. Аудитории, кафедры и фотографии не являются списываемым оборудованием.

Добавить:

| Поле | Назначение |
| --- | --- |
| `status` | `ACTIVE` или `WRITTEN_OFF`, обязательное; новые и перенесенные записи по умолчанию `ACTIVE` |
| `written_off_at` | Дата последнего действующего списания; nullable |
| `written_off_by` | ФИО сотрудника, выполнившего списание, до 255 символов; nullable |
| `last_modified` | Время последнего изменения записи |
| `changed_by` | ФИО автора последнего изменения, до 255 символов |
| `version` | Версия для защиты от перезаписи одновременных изменений |

Статус можно хранить строкой с ограничением допустимых значений в БД и Java enum в коде. Для `ACTIVE` поля действующего списания пустые; для `WRITTEN_OFF` заполнены оба поля. Пользователь не задает даты и служебные поля произвольно.

### 5.8. Доска

Добавить nullable `board_type`: `CHALK` — «Меловая», `MARKER` — «Маркерная». Для старых и незаполненных записей использовать `NULL`, в интерфейсе — «Не указано».

Поле доступно в создании, редактировании, карточке, таблице и фильтрах. Значения «Нет доски» и «Оба типа» в этой версии не вводить. `NULL` обозначает неизвестный тип, а не подтвержденное отсутствие доски.

### 5.9. Фотография

`auditorium_photo`: `id`, обязательный `auditorium_id`, `file_path` до 1024 символов, `original_filename` до 255 символов, `content_type` до 255 символов. Добавить сведения об авторе и времени добавления; использовать общие `changed_by`, `last_modified`. Для проверки удаления предусмотреть `version`.

В БД хранится метаинформация, файл находится в файловом хранилище. Правила работы с файлами описаны в разделе 9.

## 6. Расчеты, списание и удаление

### 6.1. Действующее оборудование

Количество компьютеров считать по `workstation` со статусом `ACTIVE`. Наличие проектора и принтера определять по существованию активных записей соответствующих таблиц. Списанное оборудование не участвует в счетчиках и фильтрах наличия.

Старые `has_projector` и `pc_count_manual` не являются источником этих расчетов. Сохранить их значения, но не редактировать через обычные формы. При расхождении показать в карточке понятное замечание о старых сведениях. Миграция не должна создавать фиктивные компьютеры или проекторы на основании только этих полей.

Не сохранять вычисляемые счетчики как независимые пользовательские значения. Запросы для таблицы и фильтров должны использовать те же правила, что карточка.

### 6.2. Списание и восстановление

Операции этого раздела применяются только к рабочим местам, проекторам и принтерам.

Списание переводит запись из `ACTIVE` в `WRITTEN_OFF`, устанавливает `written_off_at`, `written_off_by`, обновляет аудит оборудования и аудитории. Запись и связь с аудиторией сохраняются в PostgreSQL.

По умолчанию в карточке отображается действующее оборудование. Предусмотреть переключатель «Показать списанное»; списанное отмечать явно и показывать дату и ФИО списания.

Повторное списание уже списанной записи не изменяет дату или автора первого действующего списания и не создает новое изменение. Повторный запрос на уже достигнутое состояние возвращает текущую запись.

Ошибочное списание исправляется отдельной операцией «Восстановить» с подтверждением и обязательным ФИО. При восстановлении статус становится `ACTIVE`, поля действующего списания очищаются, обновляются сведения о последнем изменении. Повторное восстановление активной записи не создает новое изменение.

Редактирование описания списанной записи допускается. Оно не восстанавливает оборудование и не заменяет ФИО или дату списания. Изменение статуса происходит только специальной операцией.

Отдельный журнал всех переходов статуса не требуется. Сохраняются сама запись, сведения о последнем изменении и данные текущего списания, когда оно действует.

### 6.3. Физическое удаление

Физическое удаление рабочего места, проектора или принтера является отдельной редкой операцией, отличной от списания. Предусмотреть ее в backend и отдельном малозаметном разделе интерфейса с явным подтверждением и обязательным ФИО. После удаления запись восстановлением статуса не возвращается.

Удаление аудитории допускается только при отсутствии связанных рабочих мест, проекторов и принтеров, включая списанные. Пока такие записи существуют, возвращать конфликт с объяснением причины. Связи с типами дополнительного оборудования удаляются вместе с аудиторией, сами записи справочника сохраняются. Кнопку удаления аудитории разместить в отдельном малозаметном разделе. Подтверждение: «Вы уверены, что хотите удалить аудиторию?». Ввода названия аудитории для подтверждения не требуется.

При удалении допустимой пустой аудитории корректно удалить ее фотографии и метаданные и освободить связи. Сбой удаления файлов обрабатывать по правилам раздела 9. Удаление кафедры при существующих ссылках аудиторий запрещено.

Не допускать удаления рабочих мест, проекторов и принтеров через замену коллекции Entity, `orphanRemoval` или общий каскад удаления аудитории. Каскад удаления связей дополнительного оборудования не должен удалять справочные типы. Настройки каскадов и внешних ключей должны поддерживать описанные ограничения.

## 7. ФИО, время и одновременное редактирование

### 7.1. Последнее изменение

Для каждой операции создания, редактирования, списания, восстановления и удаления обязательна непустая строка ФИО до 255 символов после удаления пробелов по краям. Не требовать строго трех слов и не проверять ФИО по списку сотрудников.

ФИО вводится вручную. Это заявленное авторство, а не подтвержденная учетная запись. Автоматически подставлять фиктивного пользователя при реальной операции нельзя.

При изменении полей аудитории, ее рабочих мест, проекторов, принтеров, фотографий или выбора типов дополнительного оборудования сервер обновляет `auditorium.last_modified` и `auditorium.changed_by`. Изменение рабочего места, проектора или принтера также обновляет собственные сведения о последнем изменении. Для кафедры и справочника дополнительного оборудования аудит ведется на самой справочной записи; редактирование ее названия не означает изменение каждой связанной аудитории.

При удалении дочерней записи аудитории обновляется аудит родительской аудитории. Для физически удаленной самостоятельной записи не обещать сохранение истории: полный журнал операций в текущий объем не входит.

Время назначается сервером. Все даты в БД остаются `TIMESTAMP WITHOUT TIME ZONE`; в Java использовать соответствующее локальное представление. Часовой пояс приложения задается конфигурацией, первоначально `Europe/Moscow`. Отображение и ответы API должны использовать единое правило времени. Клиент не задает `last_modified` и `written_off_at`.

При миграции не придумывать ФИО и даты старых изменений. Неизвестные исторические значения можно оставить `NULL`; при первой новой операции они заполняются.

### 7.2. Защита от потери изменений

Добавить `@Version` к изменяемым сущностям и поле `version BIGINT NOT NULL DEFAULT 0` в БД; существующие записи начинают с версии 0. Формы и API передают прочитанную версию записи. При конфликте одновременного изменения вернуть `409 Conflict`, объяснить, что запись уже изменена, и сохранить введенные пользователем значения в форме.

Для повторного запроса списания или восстановления, когда запрошенное состояние уже достигнуто, возвращать текущую запись без изменения данных и аудита. Проверка версии обязательна, если запрос действительно меняет состояние.

Не перезаписывать чужое изменение автоматически и не повторять конфликтующий запрос с новой версией без действия пользователя. Предложить обновить данные и повторно сверить изменения.

При изменении дочернего оборудования или фотографий обновлять также аудит и версию аудитории в той же транзакции. Для создания дочерней записи или загрузки фотографии передавать прочитанную версию аудитории. Для изменения и удаления существующего оборудования проверять его собственную версию; общую аудиторию обновлять с соблюдением optimistic locking.

При добавлении или удалении связи с типом дополнительного оборудования проверять версию аудитории и обновлять ее аудит и версию. Отдельная версия самой записи связи не требуется. Редактирование справочного типа проверяет версию этого типа.

## 8. REST API и ошибки

### 8.1. Общие правила

Все изменения интерфейса проходят через `/api/**`. API чтения также сохраняется как самостоятельная возможность backend. Запросы и ответы используют DTO, служебные поля назначения времени и автора нельзя подменять произвольным обновлением Entity.

API должен документировать HTTP-метод, URL, запрос, ответ, обязательные поля, проверки и коды ошибок. В JSON использовать единый стиль имен полей, например camelCase; в PostgreSQL сохранить snake_case.

ФИО операции передавать как `changedBy`. Версию при обновлении — как `version`. Создание дочернего объекта передает `auditoriumVersion`. При загрузке фотографии эти же сведения передаются отдельными частями multipart-запроса.

Для `DELETE` использовать параметры `changedBy` и `version`, чтобы не зависеть от поддержки тела DELETE-запроса. Проверять их на сервере так же, как поля JSON. Удаление остается отдельным HTTP-запросом, а не GET-ссылкой.

Для `PUT` передавать полный набор редактируемых полей соответствующей формы; пустое необязательное поле очищает его значение. `schedule_link`, `actual_schedule_link`, старые расчетные признаки, статус, даты и другие поля вне формы не включать в обычный DTO редактирования аудитории или оборудования и не очищать при таком обновлении. Списание и восстановление выполняются своими endpoint.

Создание возвращает `201 Created`, чтение и изменение — `200 OK`, успешное удаление — `204 No Content`. Отсутствующая запись — `404`, неверные значения — `400`, конфликт версии, связи или уникальности — `409`, превышение размера запроса — `413`, неподдерживаемый тип файла — `415`.

### 8.2. Аудитории и кафедры

```text
GET    /api/auditoriums
GET    /api/auditoriums/{id}
POST   /api/auditoriums
PUT    /api/auditoriums/{id}
DELETE /api/auditoriums/{id}

GET    /api/departments
GET    /api/departments/{id}
POST   /api/departments
PUT    /api/departments/{id}
DELETE /api/departments/{id}
```

`GET /api/auditoriums` поддерживает поиск, фильтры и серверную пагинацию из раздела 10. Ответ содержит DTO записей и сведения о странице, размере, числе элементов и числе страниц.

### 8.3. Оборудование

Для каждого ресурса `workstations`, `projectors`, `printers` реализовать:

```text
GET    /api/auditoriums/{auditoriumId}/{resource}
POST   /api/auditoriums/{auditoriumId}/{resource}
GET    /api/{resource}/{id}
PUT    /api/{resource}/{id}
PATCH  /api/{resource}/{id}/write-off
PATCH  /api/{resource}/{id}/restore
DELETE /api/{resource}/{id}
```

`{resource}` означает одно из трех имен выше, например `/api/auditoriums/101/workstations` или `/api/projectors/7/write-off`.

Списки оборудования по умолчанию возвращают `ACTIVE`. Параметр `includeWrittenOff=true` включает также списанные записи. Ответ содержит статус, версию и сведения о списании. При списании или восстановлении интерфейс должен получить обновленную запись и затем обновить карточку с актуальными счетчиками.

### 8.4. Справочник дополнительного оборудования и связи

```text
GET    /api/additional-equipment
GET    /api/additional-equipment/{id}
POST   /api/additional-equipment
PUT    /api/additional-equipment/{id}
DELETE /api/additional-equipment/{id}

GET    /api/auditoriums/{auditoriumId}/additional-equipment
POST   /api/auditoriums/{auditoriumId}/additional-equipment
DELETE /api/auditoriums/{auditoriumId}/additional-equipment/{additionalEquipmentId}
```

Общие endpoint работают со справочными типами. Вложенный GET возвращает выбранные для аудитории типы. Вложенный POST добавляет связь с уже существующим типом; передаются `additionalEquipmentId`, `changedBy`, `auditoriumVersion`. Вложенный DELETE снимает выбор типа; параметры `changedBy` и `version` относятся к этой операции и версии аудитории. Создание типа и его привязка к аудитории — разные операции.

Удаление справочного типа допускается только при отсутствии связей; иначе вернуть `409 Conflict`. Изменения связей обновляют аудит и версию аудитории. Статусов, параметра `includeWrittenOff` и endpoint `write-off` или `restore` у дополнительного оборудования нет.

### 8.5. Фотографии

```text
GET    /api/auditoriums/{id}/photos
POST   /api/auditoriums/{id}/photos
GET    /api/photos/{photoId}/content
DELETE /api/photos/{photoId}
```

Список фотографий возвращает метаданные и URL получения изображения. Загрузка использует `multipart/form-data`, части `file`, `changedBy`, `auditoriumVersion`. Один файл в одном запросе. Endpoint содержимого возвращает файл с корректным MIME type. Абсолютный путь на диске не раскрывается в ответах.

### 8.6. Ошибки и валидация

Использовать `@RestControllerAdvice` и единый JSON-формат ошибок. Например:

```json
{
  "timestamp": "2026-10-03T12:00:00",
  "status": 400,
  "error": "Bad Request",
  "message": "Проверьте заполнение формы",
  "path": "/api/auditoriums",
  "fieldErrors": {
    "name": "Укажите название аудитории"
  }
}
```

`fieldErrors` использовать для ошибок полей. Пользовательские сообщения показывать на русском. Не выводить пользователю stack trace, SQL и внутренние пути. Ошибки открытия HTML-страниц оформлять как понятные страницы с навигацией обратно.

Использовать Bean Validation и ограничения БД для обязательных значений, неотрицательных чисел, допустимых enum и длины строк. Непустые пользовательские названия и ФИО очищать от пробелов по краям; пустые необязательные строковые поля трактовать как отсутствие значения.

URL-поля `schedule_link`, `actual_schedule_link`, `cartridge_link`, `mol_link` не требуют строгой проверки корректности URL. Проверять длину; при отображении не допускать выполнения содержимого как HTML или скрипта.

Исключения создавать для понятных случаев отсутствия записи, конфликтов и ошибок хранения; не делать отдельный класс для каждой мелкой ошибки. JavaScript улучшает обратную связь, но сервер всегда выполняет окончательную проверку.

## 9. Фотографии и файловое хранилище

Пользователь может добавлять, просматривать и удалять фотографии аудитории. Для добавления и удаления обязательны ФИО; для удаления — подтверждение.

Разрешены JPG, JPEG и PNG. WEBP не поддерживается. Максимальный размер одного файла — 10 000 000 байт. Настроить лимиты multipart-запроса с учетом служебных частей так, чтобы разрешенный файл не отклонялся из-за заголовков multipart.

Проверять:

- расширение `.jpg`, `.jpeg`, `.png` без учета регистра;
- MIME type: `image/jpeg` или `image/png`;
- размер и наличие содержимого;
- фактический формат файла по содержимому, а не только заявленный клиентом MIME type.

Фотографии хранить в файловой системе через интерфейс `FileStorageService` и реализацию `LocalFileStorageService`. Корневой каталог задается конфигурацией. Бизнес-сервисы не работают напрямую с `java.io.File` и не зависят от конкретного диска.

Новые физические имена формировать на сервере, например с UUID. Исходное имя сохраняется как метаданные. Новое `file_path` хранит относительный ключ внутри хранилища. Не использовать пользовательское имя для построения пути; операции ограничивать корневым каталогом хранилища.

Если старые фотографии имеют другой формат путей, сначала проверить наличие файлов и подготовить перенос или совместимое чтение. Не переписывать метаданные путей без учета самих файлов.

БД и файловая система не имеют общей транзакции. Поэтому:

1. При загрузке сначала проверить файл, ФИО, аудиторию и версию; если файл сохранен, а запись БД не создана, удалить созданный файл либо зарегистрировать неудачную очистку для повторного выполнения.
2. При удалении сначала успешно завершить удаление метаданных и изменение аудита в БД, затем удалить физический файл. Если удаление файла не удалось, записать задачу или запись для повторной очистки и сообщить об ошибке в техническом журнале.
3. При сбое операции до commit метаданные не должны ссылаться на уже удаленный файл.
4. Не оставлять ошибки хранения скрытыми и не выдавать сбой загрузки за успешное добавление фотографии.

Для повторной очистки достаточно простого механизма внутри приложения; внешние очереди и отдельный сервис не требуются. Возможность будущего серверного или S3-хранилища обеспечивается интерфейсом, а дополнительные реализации сейчас не разрабатываются.

## 10. Поиск, фильтры и пагинация

Общий поиск — по подстроке названия аудитории без учета регистра. Значение поиска очищать от внешних пробелов. Поиск по инвентарным номерам `pc_name` не входит в общий поиск.

Расширенные фильтры:

- тип аудитории;
- корпус;
- этаж;
- наличие активного проектора;
- наличие активного принтера;
- наличие активных рабочих мест;
- наличие интернета;
- наличие кондиционера;
- тип доски;
- кафедра.

Выбранные фильтры и текст поиска объединять условием AND. Корпус и этаж фильтруются по выбранному значению, кафедра — по идентификатору. Для фильтров по nullable-признакам «Да» соответствует `true`, «Нет» — `false`; неизвестное значение не приравнивается к «Нет». Не выбранный фильтр не ограничивает результат.

Диапазон вместимости не добавлять. Дополнительные фильтры без конкретной необходимости не вводить.

Расширенные фильтры скрыты за кнопкой «Фильтры». Есть кнопка «Сбросить фильтры». Поиск и фильтры отправляются обычной GET-формой и представлены в query-параметрах URL.

Серверная пагинация обязательна. По умолчанию 20 записей, доступны 20, 50 и 100. API не должен отдавать неограниченный список аудиторий; неверные параметры страницы и размера отклонять. Для API `page` начинается с нуля, в интерфейсе пользователю показывать номера с единицы.

Использовать стабильную сортировку: корпус, название, затем `id`; для пустых значений определить единый порядок. Набор сортировок пользователю в первой версии не требуется. При изменении поиска, фильтра или размера страницы возвращаться на первую страницу.

Список для HTML и список API используют один сервис поиска и одинаковые правила. Запросы должны корректно совмещать пагинацию с отношениями оборудования, без дублирования аудиторий в выдаче.

При переходе в карточку и обратно сохранять поиск, фильтры, страницу и размер через параметры URL. Параметр возврата ограничить внутренним маршрутом приложения.

## 11. Интерфейс и работа с телефона

### 11.1. Страницы

Начальная страница — список аудиторий. Предусмотреть MVC GET-маршруты списка, карточки, создания и редактирования аудитории, а также раздела кафедр. Конкретные дополнительные маршруты форм оборудования определить по мере реализации без дублирования API-сохранения.

Карту «Аудитории 360» использовать как ориентир навигации. Разделы «Заявки» и «Статистика и управление» пока являются страницами-заглушками с пояснением о будущей реализации. Формы заявок, графики, авторизация и настройка доступа в эту версию не входят. Учет аудиторий, оборудования, фотографий и справочники работают по требованиям ниже.

### 11.2. Формы и подтверждения

Формы имеют русские подписи, обязательность полей обозначена явно. ФИО обязательно для отправки изменения. Скрытые служебные данные включают версии записей.

Перед сохранением создания или редактирования записи показывать простое подтверждение «Вы уверены, что хотите сохранить изменения?». Перед списанием, восстановлением и удалением показывать подтверждение конкретного действия. Для добавления фотографии отдельное модальное подтверждение не обязательно: выбор файла и кнопка загрузки являются явным действием пользователя.

Для подтверждений достаточно обычного JavaScript `confirm`; сложная система модальных окон не требуется. Отмена подтверждения не отправляет запрос. Подтверждение интерфейса не заменяет серверные проверки ФИО, версии и бизнес-правил.

При отказе сервера, сетевой ошибке или конфликте не очищать форму. После успешного сохранения показывать результат и переходить к актуальной карточке с сохранением контекста списка.

### 11.3. Адаптивность

Цвета: синий, белый, светлые оттенки серого. Дизайн простой, аккуратный, без лишней анимации.

Таблица, формы, карточки, фотографии, кнопки, поиск, фильтры и пагинация должны быть удобны на компьютере и телефоне. На узком экране таблицу можно адаптировать или прокручивать внутри отдельного контейнера; вся страница не должна расползаться по ширине. Основные действия доступны без наведения мыши.

Отдельное мобильное приложение не требуется. На сервере телефон открывает обычный адрес сайта в браузере.

Доступ с телефона по IP компьютера в общей локальной сети — необязательный способ внутреннего тестирования во время разработки. Это не обязательный пользовательский сценарий развернутого приложения и не отдельная функция. При необходимости в README можно описать такой способ проверки.

## 12. JPA, качество кода и проверки

Использовать JPA/Hibernate с учетом lazy loading, N+1, каскадов, `orphanRemoval` и optimistic locking. Не включать `EAGER` только для устранения ошибки загрузки. Отношения загружать под конкретный запрос или DTO; не выполнять отдельный запрос на оборудование каждой строки списка.

Не заменять коллекции рабочих мест, проекторов и принтеров так, чтобы это приводило к физическому удалению старых записей. При изменении выбранных типов дополнительного оборудования удалять только записи связи, сохраняя справочник. Вычисления вместимости и оборудования должны соответствовать этой спецификации, включая `NULL` и статусы. Текущие `@Formula`, учитывающие все рабочие места или заменяющие неизвестное число нулем, пересмотреть.

Имена классов, методов и полей должны быть понятными, стиль — последовательным. Комментарии объясняют неочевидное решение, а не повторяют строку кода. Избыточные интерфейсы, абстракции и зависимости не добавлять.

Проверки выбирать по риску изменения. Нужны содержательные проверки миграций и основных сценариев:

- запуск и миграции на чистой и ранее заполненной БД;
- сохранение исторических значений и правильный перенос связей;
- создание и обновление аудитории, обязательные поля, `NULL`, ноль и длина строк;
- поиск, совместная фильтрация, пагинация и стабильность выдачи;
- отсутствие второго пути сохранения через MVC;
- подсчет только активного оборудования всех нужных видов;
- списание, повторное списание, восстановление и редактирование списанного рабочего места, проектора и принтера;
- сохранение справочника дополнительного оборудования, добавление и удаление связей без удаления типов и без списания;
- запреты удаления аудитории с оборудованием и используемой кафедры;
- обязательное ФИО и обновление аудита родительской аудитории;
- конфликт одновременного изменения без потери пользовательского ввода;
- допустимые и ошибочные загрузки фотографий, ошибки хранения и очистки;
- резервное копирование и восстановление БД вместе с файлами;
- работа интерфейса на узком экране.

Интеграционные проверки особенностей PostgreSQL, включая исходный enum и миграции, выполнять на PostgreSQL, а не считать поведение другой СУБД равнозначным. Тесты используют отдельную тестовую БД или временные контейнеры; реальные данные в них не применять.

Для небольших изменений внешнего вида достаточно подходящей визуальной проверки. Не создавать тесты, которые только повторяют реализацию и не проверяют полезное поведение.

В конце этапа кратко сообщать, что создано или изменено, как проверено и какие конкретные препятствия остаются. Не отмечать этап завершенным, если обязательные проверки не выполнены. ## 15. Критерии готовности

Первая версия считается готовой, когда:

1. Существующие данные безопасно перенесены, чистая БД создается через миграции, неоднозначные связи не потеряны.
2. Страницы формируются MVC и Thymeleaf; все изменения интерфейса выполняются через REST API и общие сервисы.
3. Аудиторию можно создать, открыть и отредактировать; необязательные и исторические поля сохраняются корректно.
4. Рабочие места, проекторы и принтеры создаются, редактируются, списываются и восстанавливаются независимо по записям. Дополнительное оборудование остается справочником типов с выбором для аудитории, без списания.
5. Списанное не участвует в активных счетчиках и фильтрах, доступно для просмотра и не удаляется обычным списанием.
6. Для всех изменений обязательно ФИО, время назначает сервер, аудит родительской аудитории обновляется.
7. Одновременное редактирование не приводит к молчаливой перезаписи чужих данных.
8. Поиск, согласованные фильтры, серверная пагинация и возврат с сохранением контекста работают.
9. Фотографии проходят проверки формата и размера, хранятся отдельно от БД и доступны после восстановления резервной копии.
10. Ограничения редких удалений соблюдаются, связанные записи не исчезают из-за каскадов.
11. Русский интерфейс удобен на компьютере и узком экране телефона.
12. Сборка, запуск, остановка, миграции и резервное копирование воспроизводятся по README.
